## Mise en situation

Avant d'appeler le moindre modèle de langage en production, il faut comprendre deux briques invisibles mais omniprésentes : la **tokenisation** (comment le texte est découpé en unités facturées et comptées dans la fenêtre de contexte) et les **embeddings** (comment une phrase devient un vecteur de nombres sur lequel on peut mesurer une proximité de sens).

Dans ce TP, vous mettez les mains dans ces deux mécanismes, entièrement en local, sans clé API ni coût. Vous comptez les vrais tokens d'une phrase avec le tokenizer d'un modèle local, vous calculez votre premier embedding avec `nomic-embed-text`, puis vous mesurez la similarité cosinus entre des phrases proches et éloignées. Vous comprendrez alors *pourquoi* deux phrases qui ne partagent aucun mot peuvent être « proches » pour un modèle : c'est exactement le socle du RAG que vous construirez au module 6.

## Objectifs

- Distinguer une tokenisation naïve « par mots » de la vraie tokenisation sous-mot (BPE) d'un LLM, et compter les tokens réels d'un texte avec le tokenizer d'Ollama.
- Calculer un embedding local avec `nomic-embed-text` et observer sa dimension.
- Mesurer la similarité cosinus entre deux vecteurs et vérifier que la proximité de sens se traduit par un score plus élevé, même sans mots communs.

## Architecture cible

```
   "Les modèles découpent le texte en tokens."
                    |
        +-----------+-----------+
        |                       |
        v                       v
  TOKENISATION              EMBEDDING
  (tokenizer llama3.2)      (nomic-embed-text)
        |                       |

              (base du RAG, module 6)

  Tout tourne en LOCAL via Ollama : aucune cle API, aucun cout.
```

3. Notez l'avertissement du code : `tokenisation_naive` découpe simplement sur les espaces et la ponctuation. Ce n'est **pas** ce que fait un LLM. Un LLM utilise un tokenizer sous-mot (BPE / SentencePiece) : un mot rare ou un mot long peut compter plusieurs tokens, et un mot fréquent un seul.

Point de contrôle : le script s'exécute sans erreur et affiche un nombre de tokens réels pour la phrase d'exemple. Comparez ce nombre au nombre de « mots » de la tokenisation naïve : ils diffèrent, ce qui montre que mots et tokens ne sont pas la même chose.

### Étape 2 — Compter les vrais tokens et estimer un coût (15 min)

Objectif : mesurer le nombre de tokens réels de vos propres phrases et comprendre l'impact sur le coût et la fenêtre de contexte.

1. Créez un fichier de travail `mon_tp01.py` dans le dossier `module-01/` (à côté du script de référence pour réutiliser la couche `common`) :

   ```python
   # module-01/mon_tp01.py
   import sys
   from pathlib import Path

   # Rendre la couche commune importable (comme dans le script de reference).
   sys.path.append(str(Path(__file__).resolve().parent.parent))

   import ollama


   def compter_tokens(texte: str) -> int | None:
       """Compte les vrais tokens via le tokenizer d'Ollama (prompt_eval_count)."""
       r = ollama.chat(
           model="llama3.2:1b",
           messages=[{"role": "user", "content": texte}],
           options={"num_predict": 1},  # on ne genere qu'un token de sortie
       )
       return r.get("prompt_eval_count")


   phrases = [
       "Bonjour.",
       "Les modèles de langage découpent le texte en tokens.",
       "anticonstitutionnellement",                 # un mot long et rare
       "L'IA générative transforme l'industrie logicielle en 2026.",
   ]
   for p in phrases:
       n = compter_tokens(p)
       mots = len(p.split())
       print(f"{n:>3} tokens | {mots:>2} mots | {p!r}")
   ```

2. Exécutez :

   ```bash
   python module-01/mon_tp01.py
   ```

3. Observez : le mot long `anticonstitutionnellement` compte plusieurs tokens alors qu'il s'agit d'un seul « mot ». À l'inverse, `Bonjour.` est très court. Le rapport tokens/mots n'est pas constant.

4. Ajoutez en fin de fichier une mini-estimation de coût, en réutilisant les chiffres de référence 2026 (Claude Opus 4.8 : 5,00 $ par million de tokens en entrée) :

   ```python
   prix_entree_par_million = 5.00  # $/1M tokens, ref. Claude Opus 4.8 (2026)
   texte = "L'IA générative transforme l'industrie logicielle en 2026."
   n = compter_tokens(texte)
   cout = n / 1_000_000 * prix_entree_par_million
   print(f"\n{n} tokens en entrée -> coût ~${cout:.8f} sur Claude Opus 4.8")
   ```

Point de contrôle : vous obtenez un nombre de tokens différent du nombre de mots, et une estimation de coût en dollars. Vous pouvez expliquer pourquoi on facture et on dimensionne la fenêtre de contexte en *tokens* et non en mots ou en caractères.

### Étape 3 — Embeddings et similarité cosinus (25 min)

Objectif : calculer des embeddings locaux et vérifier que la proximité de sens se traduit par une similarité cosinus plus élevée.

Ajoutez ce bloc à votre fichier `mon_tp01.py` (ou créez-en un nouveau) :

```python
import numpy as np
from common import embed   # couche commune : embed(text) -> liste de floats via Ollama


def cosine(a, b) -> float:
    """Similarite cosinus : 1 = identiques, 0 = orthogonaux, -1 = opposes."""
    va, vb = np.array(a), np.array(b)
    return float(np.dot(va, vb) / (np.linalg.norm(va) * np.linalg.norm(vb)))


# Trois phrases : P1 et P2 parlent du meme theme (sans partager les memes mots),
# P3 parle d'autre chose.
p1 = "J'adore développer des applications en Python."
p2 = "La programmation logicielle est ma passion."        # theme proche de P1
p3 = "La recette du gâteau au chocolat est délicieuse."   # theme eloigne

v1, v2, v3 = embed(p1), embed(p2), embed(p3)
print("Dimension d'un embedding :", len(v1))

sim_proche = cosine(v1, v2)
sim_loin = cosine(v1, v3)
print(f"similarité(P1, P2) = {sim_proche:.3f}  (sens proche)")
print(f"similarité(P1, P3) = {sim_loin:.3f}  (sens éloigné)")
assert sim_proche > sim_loin, "La phrase de sens proche devrait scorer plus haut."
print("OK : la proximité de SENS donne un cosinus plus élevé, sans mots communs.")
```

1. Exécutez le fichier et lisez la dimension affichée : `nomic-embed-text` produit des vecteurs de 768 dimensions.
2. Vérifiez que `similarité(P1, P2)` est nettement supérieure à `similarité(P1, P3)`. P1 et P2 ne partagent pourtant aucun mot significatif : c'est le *sens* qui est capté, pas les mots.
3. Expérimentez : remplacez P3 par une phrase qui parle, elle aussi, de programmation (par exemple `"Je code surtout en Java au travail."`) et relancez. Le score de P3 devrait se rapprocher de celui de P2.

Point de contrôle : l'assertion `sim_proche > sim_loin` passe sans déclencher d'erreur, et vous savez expliquer que c'est précisément ce mécanisme (chercher les chunks dont l'embedding est le plus proche de la question) qui permettra la *récupération* dans un système RAG.

## Dépannage courant

<details>
<summary>Erreur : connexion refusée / `Connection refused` sur localhost:11434</summary>

Cause : le serveur Ollama n'est pas démarré.
Solution : lancez le serveur dans un autre terminal avec `ollama serve` (ou ouvrez l'application Ollama). Vérifiez ensuite avec `ollama list`.

</details>

<details>
<summary>Erreur : `model 'nomic-embed-text' not found` ou `model 'llama3.2:1b' not found`</summary>

Cause : le modèle n'a pas été téléchargé.
Solution : exécutez `ollama pull nomic-embed-text` et `ollama pull llama3.2:1b`, puis relancez. Le premier appel après un `pull` peut être un peu lent (chargement en mémoire).

</details>

<details>
<summary>Erreur : `ModuleNotFoundError: No module named 'common'`</summary>

Cause : le script n'a pas ajouté le dossier `code/` au chemin d'import, ou il est lancé depuis le mauvais répertoire.
Solution : conservez la ligne `sys.path.append(str(Path(__file__).resolve().parent.parent))` avant l'import de `common`, et lancez le script depuis le dossier `code/` (par exemple `python module-01/mon_tp01.py`).

</details>

<details>
<summary>Le score `prompt_eval_count` renvoie `None`</summary>

Cause : sur certaines versions, le compteur n'est renseigné qu'après un premier appel « à chaud ».
Solution : relancez le script une seconde fois ; le modèle est alors déjà chargé et le compteur est renseigné.

</details>
